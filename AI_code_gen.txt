PROMPT 3 -- 2026-09-15 -- failure-mode analysis and guards
================================================================================

VERBATIM PROMPT:

    TASK: assess possible failure modes for your matvec_multiply function, and
    add logic to guard them

WHAT THE MODEL DID:

Probed the existing implementation with deliberately malformed inputs to find
real failure modes, rather than reasoning about them abstractly. Three classes
were found and confirmed by execution:

  1. Silent wrong answers (most serious -- nothing signalled a bad result):
       - a nan or inf entry propagated through and was returned;
       - [1e308, 1e308] . [1, 1] returned inf;
       - naive left-to-right summation of [1e16] + [0.1]*1000 lost all 100
         from the small terms, returning 1e16 instead of 1e16 + 100.
  2. Cryptic errors that pointed at the arithmetic instead of the caller's
     mistake: a flat list passed as a matrix reported "object of type 'int' has
     no len()"; a string entry reported an unsupported += operand; likewise for
     None entries, generators, and a None row.
  3. An unchecked path: matrix_vector_product([], anything) returned [] without
     ever examining the vector.

Guards added for each:

  - Structural checks rejecting scalars, generators, strings, bytes, and flat
    lists passed as matrices, with messages naming the argument.
  - Entry checks rejecting non-real values, including strings (important
    because "ab" * 2 is a string rather than an error) and complex numbers.
  - Finiteness checks rejecting nan and inf inputs, and integers too large to
    convert to float.
  - An overflow check on the result, so a sum leaving the float range raises
    OverflowError instead of returning inf.
  - Neumaier compensated summation in place of the naive running sum, which
    removed the precision loss entirely (the 1e16 case is now exact).
  - The empty-matrix shortcut now validates the vector before returning [].

Seventeen tests were added for the new guards, bringing the suite to 40.

VERIFICATION RUN BY THE MODEL:

  - All 40 tests passed; every probed failure mode now produced a clear, typed
    error, and the precision case became exact.
  - Mutation test: stripping every guard back out failed 8 of the 40 tests.

NOTES RAISED BY THE MODEL:

  - The 1000x1000 benchmark slowed from ~0.019 s to ~0.12 s, split between the
    per-element checks and the compensated summation.
  - Booleans still pass as numbers, since bool subclasses int.

COMMIT: 28def9e  "Guard matvec functions against malformed and unsafe input"

PROMPT 4 -- 2026-09-16 -- audit of the preceding work
================================================================================

VERBATIM PROMPT:

    Review the prompts that I provided and double check all the tasks were
    accurately implemented and tested throughly.

WHAT THE MODEL DID:

Audited the work against the original comment stubs (retrieved from commit
4de43a5) rather than against its own summaries, and measured line coverage with
the standard library's trace module. Four genuine problems were found:

  1. A SPEC REGRESSION INTRODUCED BY THE MODEL ITSELF IN PROMPT 3.
     The original stub reads "create a function to compute the matrix-vector
     product using the dot_product function". While adding guards, the model
     had rerouted matrix_vector_product through a private unchecked kernel for
     speed. Instrumentation confirmed dot_product was called 0 times for a
     two-row matrix. No test had asserted the relationship, so nothing caught
     it. Fixed: the kernel was folded back into dot_product, which is now
     called once per row (verified: 2 calls for 2 rows), with row context
     re-attached to propagated errors so messages still name matrix[i][j].
     Cost: the benchmark moved from ~0.12 s to ~0.18 s.

  2. main() HAD NO TEST COVERAGE. It is one of the three functions the stubs
     asked for, and all 18 of its lines were unexecuted by the suite. A smoke
     test now captures its stdout and asserts its self-check prints True.

  3. A MAPPING PASSED THE GUARD AND PRODUCED A NUMBER.
     dot_product({0: 1, 1: 2}, [1, 2]) returned 5.0, because a dict has both
     __len__ and __getitem__ and so satisfied the duck-typed check -- exactly
     the silent-wrong-answer class prompt 3 was meant to close. Mappings are
     now rejected.

  4. TWO GUARDS WERE UNTESTED IN SUBSTANCE. Deleting the ragged-row check or
     the column-count check failed no test, because dot_product's own length
     check still raised ValueError and the tests asserted only the exception
     type. Behavior stayed correct; the diagnostic quality silently degraded.
     Those tests now assert message content.

The suite grew from 40 to 47 tests.

VERIFICATION RUN BY THE MODEL:

  - Line coverage (stdlib trace): every line of matvec_multiply.py is executed
    by the suite except the main() call under the __main__ guard, which cannot
    be reached from an imported test module.
  - Mutation testing with nine injected defects -- * changed to +, compensation
    discarded, last matrix row skipped, and removal of each of the overflow,
    finiteness, ragged-row, column-count, mapping, and dot_product-delegation
    guards. All nine are now detected by the suite. Two of them (ragged-row and
    column-count) survived the first attempt, which is what exposed finding 4.

NOTES RAISED BY THE MODEL:

  - This was the model auditing its own work and therefore shares its blind
    spots; the mutation results are the most trustworthy part, being mechanical.
  - Two behaviors were flagged and deliberately left unchanged: booleans are
    accepted as numbers, and matrix_vector_product([[]], []) returns [0.0],
    one empty sum per row.
